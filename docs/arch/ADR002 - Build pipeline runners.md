## Decision

<!-- 
    In a few sentences, describe the decision taken. 
-->

The decision has been made to go with Option 1 (Self-hosted runners) for now. If there is a decision made by the DfE to allow the Github hosted runners, then we will likely switch to Option 2.

The reason for this decision, is that we do not have a timeline on when we would have Github hosted runners made available to us, and using self-hosted runners will prevent us from getting blocked by another team for this piece of work.

**Update 05/11/2026**

The above decision has since been changed.
A new 3rd option (now option 1) has been introduced, which is to use Github hosted runners with Scripts to access Azure.

This new option is different from the original GHR (Github hosted runners) option, as that was considering using a feature of Azure that allowed GHR to access a private network.
Instead the new option simply has scripts in the infrastructure/scrips folder to grant & remove access to required resources, and the workflow will call those scripts as and when they are needed.

## Context

<!-- 
    Describe the forces and circumstances that brought about this decision. 
-->

The build pipeline for the application requires access to the data generated by the data pipeline (web scraper).
This data is in a storage account within the Azure infrastructures private network, and has public network access disabled.

We have considered 3 options (initially 2) to get around this issue.

### Option 1 - Github hosted runners + azure access scripts

Positives:

- Require little to no maintenance, the runners are under Githubs control

Negatives:

- If there are changes to the infrastructure we need to be sure to update the scripts used to grant access


### Option 2 - Self-hosted runners

Positives:

- Manageable within the team, no external dependencies

Negatives:

- Requires more set-up / overall maintenance time

### Option 3 - Github hosted runners within the private network

Positives:

- Github hosted runners require little to no maintenance

Negatives:

- This requires collaboration with the wider DfE Digital Tools / Infrastructure teams, to co-ordinate the configuration

John Carter suggested that the Github Hosted Runners (Option 2) would be the sensible option to go with, and this is our preferred implementation.
However, he also advised that the lead-time on getting Github Hosted Runners would be quite long, as it is a decision that must be made by the DfE Enterprise Team.

Pradeep Neelakandan has advised the team to go with Self-Hosted (Option 1), at least until a formal decision is made by the enterprise team.

**Update 05/11/2026**

The decision was recently made to change our approach to the build runners.
We had initially gone with [Option 2](#option-2-self-hosted-runners) but were experiencing issues with getting these to work alongside Github.

After some investigation & consideration we instead decided to go with a new option ([Option 1](#option-1-github-hosted-runners-+-azure-access-scripts)).
We had initially ruled out this option due to believing it was not possible, but after spending some dedicated time on it we were able to get it working.
This decision was approved by Pradeep Neelakandan, and the architecture and access scripts were reviewed and approved by Hari Katkam.
